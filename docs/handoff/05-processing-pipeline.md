# 05. Пайплайны обработки

## Сбор источника

1. Scheduler выбирает `enabled=true` источники с наступившим `next_run_at`.
2. Worker получает URL с rate limit, timeout, conditional headers (`ETag`, `Last-Modified`) и безопасным retry.
3. Сохраняются raw response и метаданные запуска.
4. Extractor извлекает основной текст, дату, заголовок, автора, external ID и canonical URL.
5. Dedup создаёт или обновляет `news_item`.
6. Classifier определяет тип, тематику, relevance score и NPA signal.
7. При необходимости LLM создаёт summary, impact и citations. Не публиковать результат без schema validation.
8. Если есть NPA signal — создать или обновить `alert`.

## Добавление НПА

### URL

API валидирует URL и создаёт `npa_tracking` в состоянии `processing`. Worker загружает страницу/документ, сохраняет snapshot, извлекает текст и создаёт первую версию. После успеха статус `active`.

### PDF

Клиент получает одноразовый URL загрузки. До обработки:

- проверка размера, MIME и magic bytes `%PDF-`;
- антивирус/песочница;
- hash и дедупликация;
- OCR только при необходимости;
- доступ к файлу строго по workspace.

## Проверка новых версий НПА

1. Worker загружает актуальный документ по canonical URL или официальному источнику.
2. Сравнивает нормализованный text/hash с последней версией.
3. При отличии создаёт новую `npa_version`.
4. Diff делит документ на статьи/пункты; текстовые сдвиги и незначимые нормализации фильтруются.
5. LLM получает только пары изменённых фрагментов и обязана вернуть объяснение с ссылками на fragment IDs.
6. Создаётся `alert`; UI «Обновления НПА» показывает только новые существенные changes.

## LLM guardrails

- Промпты требуют: не выдумывать норму, объяснять только переданный фрагмент, явно указывать недостаток данных.
- Сохранять входной document/version hash, prompt/model version, ответ, latency и стоимость.
- Цитаты должны ссылаться на исходный fragment ID; UI открывает оригинал по этой ссылке.
- Высокий риск: правила маршрутизации на review человеком, а не автоматическая юридическая рекомендация.

## Retry и дедупликация

Задачи имеют `idempotency_key`. Retry: экспоненциальная задержка с лимитом. Ошибка конкретного источника не должна блокировать остальные. Любой worker можно безопасно запустить повторно.
